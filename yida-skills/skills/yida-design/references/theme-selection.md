# 共享主题选择与项目化规则

Fast、Plan 和单页设计共用 [主题索引](../templates/design-themes/index.json) 与其中列出的完整主题。命名模板共用这一主题库；另有独立的自由创意路径，不要求匹配模板。详见[应用风格模板与自由创意](application-style-library.md)。

## 已选风格只确认一次

每次进入设计或准备风格问题前，先检查当前用户回答、`brief.visualSelection`、已有方案的 `visualStyle.internal.selectedTheme` 和当前应用 `design.md` 的 `themeProfile.sourceThemeId`。以同一任务中用户最新的明确选择为准；存在可复用选择就直接继续设计，不展示新一轮候选。

- 用户选中主题、自由创意或推荐项后，选择即完成。配色、Token 或页面布局未完成时，由 AI 补齐，不重新询问风格。
- 先保存 `visualSelection.themeId` 和 `visualDirection.source`：选项回答记为 `user_selected`，直接指定记为 `user_explicit`。Plan 沿用到 `visualStyle.internal.selectedTheme`；补设计细节时保留原选择来源。
- 名称、编号或“用推荐的”按当时的候选映射确定 ID。文件缺失时从真实历史回答恢复；映射不清时只澄清具体歧义，不重发整套候选。较早交互的迟到回传不能覆盖用户后来的选择。
- PRD 生成、修改或确认之后，以及切换 Skill、恢复任务、补齐 pendingFields 时，都直接复用选择。“拒绝第一直觉”只作用于首次提出候选前的 AI 内部比较。
- 只有用户主动明确要求换风格，才开始新的选型。实现冲突只处理冲突的具体要求，保留已选主题；整体方案确认不包含再次选风格。

## 输入与优先级

先读取已确认需求、现有应用主题和视觉证据；页面内容、导航类型、数据、字段、流程和权限沿用业务规划。视觉证据按以下顺序处理：

```text
用户明确视觉要求
> 品牌规范、Logo、官网、参考图和已有设计
> 业务场景、使用频率、信息密度和主要终端
> AI 补齐
```

将“简洁、专业”等描述落实为导航、应用框架、表单、记录详情和自定义页面的表面层次、边界强度、形状分工、文字节奏、色彩强调和组件状态。行业、颜色、主题名称或“有图表/表格/右栏”等公共组件不能单独决定主题。索引摘要用“深色/浅色导航”和“深色/浅色内容界面”自然描述明暗关系；默认选择浅色内容主题，已明确暗色、夜间或同等视觉要求时选择对应暗色内容主题。导航明暗采用最终主题模板的 `navTheme`，用户明确的导航明暗作为主题筛选约束，不在主题选定后独立猜测或覆盖。

## 高频管理场景的适配判断

先判断用户每天做什么，再判断行业气质。高频查阅、比较与处理任务，首先比较数字扫描、筛选与批量操作、状态辨认以及原生表格和表单的连续使用体验。行业与对象名称不等于用户要求奶油、咖啡、复古或大面积暖黄。

没有明确品牌或整体配色要求时，优先用低饱和近白画布、清楚的内容面、中性正文和局部品牌强调建立层次；主色仍由项目决定，不固定为蓝色。命名模板的纸纹、黄底、金棕导航或大面积彩色表面必须有任务或视觉证据支持，不能因“更有表现力”自动胜出。用户明确要求这些风格时予以保留，并保证文字、状态和表格可读。

比较方向时，`recommendationReason` 说明它如何支持当前高频任务；`visualDirection.description` 说明导航、内容和主操作的层次，`colorStrategy.usage` 区分大面积背景、中性文字和局部强调。沿用现有字段，不另造评分体系。通用示例的颜色、主题排列顺序和预览色都不是默认推荐。

按[任务驱动的视觉设计](task-driven-visual-design.md)推导信息表达与图片价值。同一对象的展示、比较、处理和回顾需要不同表现，行业相同不代表页面结构或材质相同。

验收同时查看原生数据管理页、提交/详情页及自定义页；检查平台外层导航与应用侧栏是否冲突、选中项是否压过主操作、搜索与分组是否过重。表格无记录、无空态提示、字段截断和横向滚动分别检查，不能把这些结构与数据问题都归因于主题或用换色掩盖。

## 波普风格的使用条件

`app-pop`（波普印刷）仅在以下任一条件成立时进入推荐、选择或效果预览：用户明确指定波普风格，或本次主要任务是品牌宣传、活动展示、作品陈列等偏展示场景。记录对应的用户原话或主要任务依据；不确定时默认排除，不为此额外问用户。

普通管理后台、审批、数据录入和日常工作台默认排除。仅有门户、图表、看板，或泛称“有创意”“看看全部风格”，不代表满足条件。前后台混合应用以本次设计的主要使用任务判断，不能因有一个展示页就给整套后台推荐波普。已有用户明确选定的波普风格继续复用，不重问。

目录保留模板供合适场景使用，`catalog` 的 `selectionEligibility` 是使用约束，不是无条件可选。候选、全部风格预览及最终映射均先过滤；不改主题模板本身。

## 先读摘要，再读选中主题

1. 比较前只读取索引的 `themes[].styleSummary`，也可用 `openyida design-plan catalog --json` 获取同一摘要。主题名称用于识别，不代替摘要中的视觉事实；不预读候选模板全文。
2. 对照摘要中的表面、轮廓、形状、文字、强调方式及偏离风险，选择最符合当前视觉要求的主题。不按关键词数量打分，不维护另一套权重或风格注册表。
3. 保留摘要中的适用条件。图表、量表、记录栈等仅按真实内容启用；没有某种内容不代表主题不适用，也不能为体现风格新增业务模块。未写明的实现细节留到主题确定后处理。
4. 选定后通过该索引记录的 `templatePath`，相对 `yida-design/` 读取一份完整主题。沿用已确认选择，不再重新推荐；用户要求比较时，按所在流程完成选择后再读全文。
5. 首次选型时，排除不符合项目要求的主题；没有合适模板时使用自由创意。品牌色等允许的项目输入不构成更换主题的理由。用户明确的导航明暗与候选主题 `navTheme` 冲突时，改选符合要求的主题，不覆盖模板的导航明暗。

主题 ID、模板路径和候选比较保留在内部实施记录；Plan 写 `visualStyle.internal.selectedTheme`，Fast 沿用 brief 的视觉选择。最终文档正文和用户可见方案只写当前项目的视觉效果、配色和使用理由，不展示模板路径或内部选择过程；design.md frontmatter 的 `themeProfile.sourceThemeId` 保留所选主题 ID，供 CLI 定位同目录配对 CSS；不把该内部字段展示为用户方案内容。实例化与验收按[模板来源约束](application-style-library.md#模板来源与重复生成)执行。

## 设计方向比较

已有选择时跳过本节。首次比较前按 [主题与导航兼容规则](navigation-decision.md#主题与导航兼容规则) 读取`openyida design-plan catalog --json` 返回的 `supportedNavigationLayouts`，排除与已确定布局不兼容的命名主题。用户只指定主题时按其允许布局规划；主题与明确布局冲突时先解决冲突，再进入候选比较。Fast、Plan、单页和美化共用该规则。

比较过程使用索引摘要与对应效果参考图，遵守上述完整模板读取边界。

Fast 与 Plan 使用下面同一套三方向生成规则和候选字段，不得分别发明候选。已有用户选择（含自由创意、采用推荐项）、明确完整风格、可信品牌规范、参考材料或应用主题时直接在其范围内完善构图与细节，不生成无意义的替代项；否则先拒绝第一直觉方案，再恰好生成三套可选的完整方向：两个命名模板方向和一个独立自由创意方向。

1. **形成三套方向**：先排除最先想到的默认方案，再围绕相同业务任务重新推演三套具有不同层次和构图的可实现方案；被排除方案不计入三套候选；不因装饰更多或色彩更强就优先推荐。每套都写 `directionId`、`directionLabel`、`description`、`recommendationReason`、`themeId`、`primaryColor` 和 `primaryColorName`；导航结构沿用业务规划，命名模板的导航明暗不作为候选输入；自由创意选定后按项目设计明确填写导航明暗与配套 Token。
2. **保证真实差异**：每个方向在构图、字体层级、表面层次、色彩关系中至少两项有明显差异；用已有内容建立重点，保留字段、操作、权限和状态。三套方向分别绑定三个不同的合法主题，其中第三项使用 free-creative 独立推演，主题索引摘要负责说明导航和内容界面的明暗。
3. **按流程选择**：Fast 在排除第一直觉后内部比较三套新方向并选择更适合的一套；Plan 仅在尚无有效选择且用户没有明确完整风格时必须展示同样三套方向并按下方宿主展示规则获得用户选择。
4. **把质感写成具体做法**：说明主次区域、数字与标题层级、背景与容器关系、间距与对齐、主操作与状态色的用法。高级感来自这些细节的一致性；表格、批量操作和异常识别保持清晰高效。
5. **一次交接**：将选定风格及业务理由写入 `visualDirection.description`，主色、背景和强调色的关系写入 `colorStrategy.usage`；AI 决定标记 `ai_default`。比较在本轮规划内完成，后续直接复用。Fast 只对用户展示选定风格和适用场景；Plan 仅在尚无有效选择时展示三套候选并请用户选择。

主色优先采用用户要求、品牌和参考图中的依据。缺少明确依据时，结合使用环境和整体构图确定配色；业务类型用于判断任务和密度，具体颜色由本项目设计确定。已确认的主色可以保留，创意也可通过构图、层级和材质表达。

## 选择时展示名称与效果图

所有环境统一使用 `ask_human` 收集风格选择，按当前宿主实际可用且当前模式允许的提问工具执行。默认只提供风格名称和一句适用说明。只有用户明确要求“给我看看风格”“展示某风格的效果”或“看全部风格”等预览时才展示效果卡片；仅要求“选择风格”不自动打开图片预览。

- 从 `openyida design-plan catalog --json` 获取名称、themeId 和可用效果图，按主题 ID 绑定图片；候选只从当前可用索引取得。没有图片时只保留标题，不留空图框、不借用其他主题图片。
- 预览范围服从用户本次请求：一款只展示一款，指定多款全部展示，要求全部则展示当前任务符合使用条件的全部风格（波普先按上述条件过滤）。常规宽屏每行 4–6 个卡片，超出换行，总行数不限；窄容器自动降为 3、2、1 列，不截断列表，不用横向滚动挤满列数。
- 卡片只包含风格标题和已有示例图，不显示描述、标签、序号、顶部说明或底部提示。HTML 只展示，不提供单选框、选中态或确认按钮，不调用 bridge 回传。
- 预览与待答问题使用同一份编号、名称、themeId 映射，不因排版重排候选。用户只要求查看时展示后结束，不额外提问；已有选择时不因看图重新选型。Plan 的默认三方向候选规则不等于预览数量限制，用户明确指定选型范围时优先遵从。
- 确需选择时，只通过一次 `ask_human` 收集。工具选项数量受限时，保留完整预览并让用户输入编号或名称，不能悄悄丢弃候选，也不硬塞图片或 HTML 到不支持的选项字段。
- 使用当前环境支持的展示方式：HTML 预览工具打开卡片页；Codex 打开生成的预览页；无 HTML 预览能力时使用图片或可打开的预览链接。聊天图片的列数由当前环境决定。遵守图片访问限制，不通过下载绕过限制。

跨环境生成只读预览页：

```bash
openyida sample yida-design theme-preview --theme-ids app-sage,app-teal,app-terminal,app-platinum --output .cache/theme-preview.html --json
```

`--theme-ids` 按用户要求的顺序传入可用主题 ID，总数不限。包含波普时还须根据真实依据传 `--pop-art-context explicit-request`（明确指定波普）或 `--pop-art-context showcase`（主要任务偏展示）；无依据时排除波普。CLI 返回预览路径与编号映射；拒绝未知、重复 ID 和覆盖已有文件，需要更新时使用新的预览路径。生成后用当前环境的预览工具打开。预览不写入用户选择。

## 拒绝第一直觉

仅在尚无可复用选择、首次为用户准备候选时执行。用户委托“根据业务场景选择合适的风格/主题”时，AI 先排除第一直觉方案，再做候选比较。排除在本轮内部完成，不新增问卷或评分字段；不能仅复核后继续采用原方案。

1. 识别最先想到的完整方案及其惯性来源，例如“销售驾驶舱 → 蓝色商务卡片”。将该方案排除，不进入后续候选、推荐或最终交付。
2. 在排除后重新生成上述三套方向（两个命名模板方向和一个自由创意方向）。各方向相对被排除方案，在构图、字体层级、表面层次、色彩关系中至少两项有实质差异；不得仅改名称、微调色值或调换候选顺序后重新引入原方案。
3. 缺少品牌或颜色约束时，至少有一个候选采用不同色相或中性主导关系，不能三套都是同一蓝色底稿只换名称；用户已明确主色时保留该主色，用其他维度形成差异。排除的是完整默认方案，不将某个颜色或主题 ID 永久列为禁用。
4. 对照数字扫描、目标与实际比较、异常辨认、长期阅读及平台页面连续性，从新方向中选出推荐项，再确定展示顺序。沿用 `recommendationReason` 和 `colorStrategy.usage` 写清业务取舍，不得仅写“专业、科技、适合销售”。

例如销售经营看板，拒绝直接套用最先想到的蓝色商务卡片方案，按日常经营复盘、目标差距追踪或投屏监控任务重新设计层级、密度和强调方式。不能为了拒绝第一直觉随机换色，也不能损害可读性和业务功能。

用户明确指定的完整风格、品牌约束、参考材料或已有满意主题优先保留，不属于需要排除的 AI 第一直觉；只给定主色时，保留主色，在其余可自主决定的维度执行排除规则。

## 交互顺序

所有宿主遵循：**基于已有信息准备候选 → 按需预览 → 同一次 ask_human 收集当前可回答的问题 → 后续方案确认（如需）**。风格题可与需求、搭建方式题一起提交，不再因阶段不同强制拆轮。

1. 已知场景足以准备候选、宿主支持多题时，将风格作为同一次 `ask_human` 的独立题，与当前必要的需求或模式问题一起提交；一题一个决定，不把多个决定混成一个选项。仅当候选确实依赖未答信息或工具题数限制时拆分，不能为了流程顺序单独再问风格。异步返回、预选、未答、关闭或超时不算答案，不因此新增提问。
2. 已有答案或明确委托就跳过相应问题，不为排序新增 `ask_human`。Fast 内部选型不增加交互，已有风格直接复用。
3. 同一任务最多一个待答交互。预览不等待另一次确认；用户只要看图时不创建选择问题，已有待答问题时保留该问题及候选映射，展示预览后继续等同一个回答。
4. 收到有效答案先保存再继续；后续搭建或美化方案确认仍在方案完成后进行。换用宿主提问工具前将旧交互记为已替代，旧回调不得覆盖当前答案。

## 千问环境的风格预览

只有用户明确要求预览且当前 `active.toolId=qwenwork` 时，才可用 `qoder_show_widget` 展示只读卡片。选择仍由 `ask_human` 收集，不等待 widget 回传。

1. 先按波普使用条件过滤，再从 catalog 按用户请求组装 `{themes: [{id, name, img}]}`，保持名称、顺序和 ID 对应；无图省略 `img`。包含波普时，data 的 `popArtContext` 仅根据真实依据填写 `explicit-request` 或 `showcase`；缺少或无效时模板不会显示波普。
2. 执行 `openyida sample yida-design theme-selector --json`。将返回的 `widget_path` 原样传给 `qoder_show_widget`，它是 **skills 根目录相对路径**；`outputPath` 仅用于定位文件。`data` 按宿主实际 schema 传入上述对象。
3. 模板只展示标题和示例图。风格选择只采纳 `ask_human` 的真实回答，不接收预览回传。
4. 无 widget 工具或展示失败时，使用跨环境预览页或宿主支持的图文展示；保持原候选，不新增选择轮次，不将未回复误判为展示失败。

## 三种流程的消费方式

| 流程 | 选择与执行 |
| --- | --- |
| Fast | 已有选择直接复用；尚无选择时按上面的共用规则排除第一直觉后生成三套方向，在内部选出推荐项并写入 brief；命名模板读取选中模板，自由创意独立编写设计与 Token，直接维护项目 `design.md`，不增加方案确认步骤 |
| Plan | 已有选择直接复用；仅无选择时按 [Plan 视觉候选规则](../sub_skill/yida-design-plan/references/visual-theme-selection.md) 展示同一组三套方向（两个模板方向和一个独立自由创意选项）；没有明确完整风格时按宿主展示规则获得用户选择；由 CLI 派生项目文档 |
| 单页设计 | 先读当前应用 `design.md` 和主题证据；沿用已确认主题，只补当前页面。尚无主题契约且需选型时读取同一索引，保持现有业务功能与应用主题 |
| 已有应用/页面美化 | 由 [ui-improve](../sub_skill/ui-improve/SKILL.md) 编排；局部修改或已有满意主题直接复用。确实需要重新选型时才使用本文件的比较规则，随后确认具体美化方案；不因选型增加重复确认或重新搭建 |

## 将主题写成项目设计

完整主题是设计底稿，按 [唯一输出契约](../workflow/output-design.md) 保留现有五章生成项目 `design.md`，不另设第二模板。阅读主题中的风格摘要、视觉系统、组件、按内容启用的特色配方及约束，再合入以下项目事实：

- 以项目名称和实际主色替换占位符，并将全部色值推导指令计算为具体 CSS 值。
- `tokens.application-global` 提供平台与页面共享的基础变量；保留 `tokens.custom-page` 中已有的独立页面语义变量，不能清空。分组仅用于组织，CSS 变量取递归叶子的原名。
- 字号、字重、行高与间距的默认值及 Tooltip 等基础契约按 [基础变量契约](../templates/design-themes/basic-tokens.json) 执行；组件选择哪些变量、圆角档位、表面和留白节奏由选中主题决定。
- 品牌色与整体氛围按 [主题与 token](../workflow/step-2-theme-system.md) 和 [用户配色优先级](../workflow/output-design.md#用户配色与模板的优先级) 处理。保留主题中可复用的层次、形状与组件机制，不能以固定灰阶覆盖用户整体配色。
- 导航按 [整体主题规则](application-theme-consistency.md#导航与应用框架) 保留完整 token、状态和消费关系；命名模板的导航明暗随模板派生，自由创意明确设计。
- 页面任务和布局来自当前业务事实，主题负责呈现。没有真实内容支撑的图形、指标、侧栏或特色配方不启用；同一应用通过页面局部变体保持统一基础语言。
- 按[指标卡与按钮配色](application-theme-consistency.md#指标卡与按钮配色)决定信息和操作的主次，将搭配写入项目组件规则。按钮和指标可用与品牌不同但协调的颜色；主题里的深色面板、近黑按钮都是可选表达，不能覆盖项目配色决定。
- 按 [视觉结构配方](visual-scaffold-recipes.md) 把真实区块映射为页面布局与八项设计要点，按 [页面质量门禁](page-quality-gates.md) 写验收条件。配方是交接辅助，不能覆盖主题节奏或生成新的业务模块。

## 交接

[输出契约](../workflow/output-design.md) 规定 token、主题 CSS、素材清单、稳定引用与运行时消费方式。最终项目文档应自包含：实现阶段只读取 PRD 和 `design.md`，不再返回主题库推断规则。

PRD 每个自定义页保留 `designFile`、`designRefs` 和一句话风格理由；完整视觉系统、具体页面设计、组件与状态规则只在 `design.md` 正文维护；frontmatter 索引用 anchor 定位。数据来源、表单入口、详情链接、权限和业务状态始终由业务契约决定。
