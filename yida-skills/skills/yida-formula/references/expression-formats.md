# 校验、动作及其他表达式

先读取目标配置，确认它接收的是公式字符串、规则对象、数据集表达式，还是 JavaScript。同一种保存方式可以用于多个设计器；照保存内容区分即可。

## 多行数据的计算顺序

输入有多条记录或多行明细时，先说明每个字段取当前行、整列，还是一组记录，再确定计算顺序。这些规则按输入数据判断，在不同页面中共用。

例如两笔收入和成本分别为 `100/50`、`1/1`：

- 每笔先算利润率再求平均：`(50% + 0%) / 2 = 25%`。
- 收入和成本分别汇总，再算整体利润率：`(101 - 51) / 101 ≈ 49.50%`。

两种结果表达不同的业务问题。先与需求对应，再从当前配置读取字段、分组和聚合设置；函数与引用按实际支持的写法填写。

## 提交校验

校验要同时保存判断公式、提示文字和是否阻断提交。确认业务含义：例如“金额小于零时阻断”，公式满足条件时是报错；而自定义校验函数通常返回 `true` 表示通过。两者不要互换。

原生公式校验编辑器保存的内容包括：

| 内容 | 用途 |
| --- | --- |
| `source` | 再次编辑时使用的字段令牌和公式 |
| `rule` 或 `rule.content` | 预处理后的执行内容，由目标配置格式决定 |
| `displayRule` | 人能读懂的公式说明 |
| `message` 和多语言提示 | 阻断时显示的文字 |
| `block` | 是否阻断，例如 `y` / `n` |
| 规则 ID、启用状态、触发时机 | 保留已有规则身份和行为 |

普通表单的原生公式校验配置在表单 `validators` 中；流程全局校验使用自己的规则包装，包含 `formulaMode`、`controlType`、`rule` 等内容。它们可以共用写公式的方法，保存时保留各自完整结构。先读取目标的完整 Schema 或流程设计，不从字段 `validation` 数组推断全部表单校验。

`EXIST` 用于查询字段值在已有记录中是否存在，涉及表单标识和预处理；按目标编辑器提供的字段填写。它不是通用的集合包含判断。去重、当前记录排除和多字段条件，应在对应提交入口核对。

目前 CLI 的 `formula check --contract validation-rule` 只检查公式部分，不生成完整校验对象或重现其预处理。原生规则没有专用保存入口时，沿用已读到的完整规则结构，通过现有设计器或适用的配置补丁保存；同一规则的 `source`、执行内容、显示内容和提示一起更新。`EXIST/EQUAL` 等经过预处理的内容应由原生编辑器生成。

### CLI 的字段校验

`create-form validation` 已有字段比较、条件必填等结构化规则。优先用这些规则表达常见需求，见 `yida-create-form-page`。

该命令的自定义 `expression/formula/source` 输入会生成 **JavaScript 校验函数**，使用 `value` 和 `getFieldValue`，例如：

```text
Number(value) <= Number(getFieldValue('numberField_stock'))
```

这里的 `value` 是当前字段值，`getFieldValue` 接收其他字段的真实 ID；`fields` 仅包含当前字段，不能当作整张表的映射。这里采用 JavaScript 运算和参数，不能直接填 `GT(#{字段ID}, 0)`。同样，自定义校验 `param.type: "js"` 保存的是 `function validateRule(value) { ... }`。完整格式见表单技能的高级模式说明。

复杂校验直接参照 [同一规则的原生公式与 JS 完整示例](nested-examples.md#同一提交规则原生阻断公式与-js-通过条件)：包含 AND/OR、跨字段取值、返回值取反、提示文字、validation 文件及业务预期。

## 业务动作

`INSERT/UPDATE/DELETE/UPSERT` 等函数配置的是数据操作。原生编辑器会提供目标表、目标字段和当前数据的令牌，并可能在保存前预处理。使用 `yida-business-rule` 选择事件和目标范围，再沿用本技能的函数与引用说明。

即使名字相同，动作中的比较函数也可能被编译成数据库条件。例如动作里的 `AND` 用于组合查询条件，不能只按浏览器的布尔运算理解。通用试算入口不执行此类写数据函数。

## 节点表达式

取数过滤、分支判断、赋值等位置可能共用 `{value, __source, __display}`：执行表达式、编辑器内容和显示文字一起保留。同样的结构出现在流程或自动化中时，共用 [节点表达式说明](automation-formulas.md)；变量前缀和函数清单仍以目标节点传入的配置为准。

通过普通流程条件自动生成的表达式还可能使用 `${fieldId} > value`。这是条件编译器的结果，不需要强行改成字段默认值公式的 `GT(#{fieldId}, value)`。

## 数据集表达式

图表计算列和数据处理中的表达式通常按数据集的字段标识计算，并涉及数据类型、分组和聚合。先读取数据集字段及函数列表，确认是“每行先计算再汇总”还是“汇总后再计算”。

原生报表配置已有 `fieldDefinition.expression`，可配合 `cubeCode`、`fieldCode`、`dataType`、`aggregateType` 和 `timeGranularityType` 使用；OpenYida 的报表 Schema 构建函数保留这些属性。具体填入哪种表达式，以目标数据集编辑器的原配置和类型检查结果为准，见 `yida-report`。

修改已有计算列时，保留原表达式、数据类型、聚合方式和日期粒度。`fieldDefinition.expression` 能保存表达式，只能证明这个结构支持表达式；还要核对当前保存命令是否接收该属性。`create-report` 的简化参数没有覆盖它时，保留完整配置并说明缺少的入口，避免静默丢掉计算列。

保存结构与公式执行分别核对。仅凭字段名或所在页面，不能认定底层使用另一套公式引擎；相同语法和执行调用可以复用已有能力，字段绑定、聚合输入或执行接口不同的部分再单独适配。验证时使用实际执行入口和相应数据，检查结果不自动跨输入方式通用。

有的编辑器中显示 `#{字段}`，保存前会转换为数据集标识；不要仅凭外观套用表单字段 ID。当前 `formula check/test` 尚未接入数据集的类型推断和执行接口；使用 `--contract dataset-expression` 会明确提示检查器未支持，不会拿表单公式规则判断它。

## JavaScript 表达式和回调

页面代码、字段事件和部分自定义校验使用 JavaScript，但取值参数由调用方决定。例如 `create-form rule` 的赋值表达式提供当前值与完整的 `fields` 映射：

```javascript
Number(value || 0) * Number(fields['单价'] || 0)
```

取值和赋值使用该回调的参数或页面 API。Canvas 页面遵循其 React 数据处理方式，平台组件页面遵循对应页面 API。原生组件如果提供默认值公式属性，再采用字段公式保存方法。

`formula check --contract javascript` 会提示使用相应 JavaScript 工具和回调上下文检查；它不会把 JavaScript 的比较符号和属性访问误报成宜搭公式错误。
